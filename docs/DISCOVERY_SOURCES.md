# Discovery source coverage

## Active compatible sources

The collection workflow uses the complete source list from the pinned FreeNodes revision. It must not filter the list down to `github_file` entries: the pinned engine also supports `web`, `password_page`, and `youtube_resources` adapters. Each source is bounded by the engine's per-source artifact/byte budgets, per-run byte budget, request timeout, concurrency, parser admission, freshness checks, and Mihomo capability checks.

At the pinned revision, the configured web discovery sources include ClashMeta, NodeV2Ray, FreeClashNode, ClashNode, OneClash, CFmem, JichangX, ClashStair, and Datiya. The active GitHub-file sources include maintained Mihomo/Clash/V2Ray subscription repositories. Password-page and YouTube-resource adapters are also configured with bounded password-candidate policies. The exact list is version-pinned in the upstream `config.yaml`; this repository's workflow prints the active adapter counts in the Actions log.

The reserve-only `audit_sources` remain inactive in the normal publication run. They are not silently promoted into production sources. In particular, MatinGhanbari's repository advertises an MIT licence for its source code but explicitly states that the aggregated proxy configurations are not covered by that licence and are not licensed for redistribution by the repository owner; Alirewa/V2ray-Configs has no repository licence declared. These large aggregate files are therefore not enabled as public subscription inputs without separate permission. This avoids turning a large candidate count into an unlicensed public re-publication of third-party node configurations.

## VPN Gate OpenVPN adapter

[VPN Gate](https://www.vpngate.net/en/) is actively queried through its official CSV endpoint, `https://www.vpngate.net/api/iphone/`. The adapter locates the CSV header, decodes each OpenVPN_ConfigData_Base64 field, parses the embedded .ovpn directives and inline CA/certificate/TLS-key blocks, and converts only the supported parameters into native Mihomo `type: openvpn` proxy entries. Official connection methods and the .ovpn workflow are documented by [VPN Gate](https://www.vpngate.net/en/howto.aspx) and [its OpenVPN guide](https://www.vpngate.net/en/howto_openvpn.aspx); Mihomo's supported OpenVPN outbound fields are documented [here](https://wiki.metacubex.one/en/config/proxies/openvpn/).

Following the source-side filter documented by CFnew's historical home-chain implementation, the adapter also excludes VPN Gate's known self-operated public VPN endpoints: hostnames beginning with `public-vpn` and addresses in `219.100.37.0/24`. This removes known directory infrastructure, not all hosting or all VPN-detected exits; every remaining volunteer relay still requires the full independent exit and risk checks. The adapter rejects profiles with missing CA material, invalid or private literal remotes, malformed ports, external credential-file references, mismatched CSV/embedded remote IPs, conflicting TLS-key blocks, or unsupported transports. CFnew's home-chain implementation is a useful transport reference: it keeps TCP VPNGate profiles, sorts by the directory's advertised speed, and adds a Cloudflare VLESS front as each OpenVPN node's `dialer-proxy`. That front can improve reachability from restrictive client networks. Its list builder uses VPNGate's advertised country field and does not independently probe the actual exit IP/country before labeling a node; NodeHub therefore keeps the real exit-IP echo and independent metadata gates. NodeHub now optionally accepts a TLS WebSocket VLESS URI through the GitHub Actions secret `NODEHUB_CF_FRONT_URI` and uses it as Mihomo `dialer-proxy` only for VPNGate CI exit probes. The secret URI/UUID is never written into public subscriptions, evidence or logs; published VPNGate entries remain direct-connect profiles. Without the secret, probes remain direct.  VPN Gate's public credentials are represented only when the profile requests auth-user-pass; certificate-based profiles use their inline client certificate and key instead. Each generated profile is checked by the pinned Mihomo binary before admission. The normal exit echo, IP metadata, Layer3 and O-X-L gates still apply afterwards.

VPN Gate official CSV contributes up to 100 candidates, the checksum-verified rolling mirror up to 200, and VPNBook up to 10 per run (310 supplemental candidates maximum). FreeNodes is configured for a 1,000-node validated pool target; the merged pre-classification candidate ceiling is 1,500. Each six-hour run performs at most 160 real-exit probes. When both supplemental source families are present, up to half of the probe budget is allocated to VPN Gate/VPNBook together, with unused quota reassigned; the remainder is allocated to FreeNodes. The GitHub run number shifts each source's sample window so successive runs test different relays rather than repeating the same sample. Upstream country, score, ping and server IP are candidate metadata only; they never prove the actual exit IP, country, residential status or risk class. If the official API is unavailable, the failure is recorded and other productive sources continue.

Mihomo supports the OpenVPN outbound; therefore VPN Gate is not excluded merely because its source format is .ovpn. An optional second HTTPS verifier is available through `IPAPI_IS_API_KEY` (GitHub Actions secret). When configured, VPNGate VPN-on-access candidates must also have `company.type=isp`, `asn.type=isp`, matching ASN/country, and explicit false values for datacenter, proxy, Tor, abuse, mobile, satellite, anycast and crawler flags. Its `is_vpn` marker is recorded but tolerated only for the exact VPNGate transport signature. The free account tier supplies 1,000 full lookups/day; without a key the anonymous tier is only 30/day and omits detection flags, so NodeHub skips this optional verifier when the secret is absent. For VPNGate, a Layer3 `vpn` signal can describe the volunteer VPN transport rather than prove the exit is hosted. NodeHub's narrow exception requires the exact VPNGate `vpn`-on-`access` signature, a fixed-line ISP operator returned by IPWHO, and a matching Layer3 access prefix/ASN classified as ISP. If O-X-L has an ASN record, it must confirm ISP and not hosting; if it has no ASN record, the exact Layer3 ASN/prefix and ISP network evidence must match. Any available O-X-L network record must have zero reports and agree with the observed ASN/prefix; any available exact-IP risk record must have zero reports. IPWHO's top-level `type` is the IP address family (for example `ipv4`), not an ISP classification. Its security fields may be absent (absence is unknown, not clean); positive proxy/Tor flags fail closed, a hosting flag conflicts with a non-hosting Layer3 classification, and a VPN flag is tolerated only for the exact verified VPNGate VPN-on-ISP-access signature. Mobile/wireless operators are excluded from the fixed-residential pool. This identifies a fixed ISP access-network exit, not proof that a specific household owns the line. The official CSV is a rolling directory (typically around 100 rows), so short-lived country entries can disappear between scheduled runs. A lightweight GitHub Actions snapshot workflow refreshes the candidate history every 20 minutes without running exit probes. It uses a non-published Actions cache (not repository commits), retains profiles for 14 days, up to 40 off-window profiles per advertised country and 2,000 profiles total, and each full run rotates a country-balanced sample of up to 100 profiles, giving US-labelled entries first look for discovery only. Profiles recovered from history are rechecked by Mihomo and then must pass the normal real-exit, ASN, Layer3 and O-X-L gates again. An old profile is not assumed live, and source country is never treated as actual exit country. The history is a private-to-the-workflow candidate cache, not a subscription; a failed API fetch with no prior cache does not overwrite a usable previous cache. VPNGate's `vpn`-on-`access` signature now has a narrow publication path, not merely an audit label. IPWHO's top-level `type` is an address family (for example `ipv4`), so it is not used as an ISP type. Admission instead requires a known fixed-line ISP operator, the exact Layer3 access IP/ASN/country/prefix match, Layer3/O-X-L ISP network evidence, no hosting conflict, and rejection of any available exact-IP/network abuse record with non-zero reports. O-X-L `not_reported` remains an unknown state and must be backed by the exact Layer3 network evidence; it is never described as a proven zero-report result. If `IPAPI_IS_API_KEY` is configured, IPAPI.is adds a second HTTPS check for ISP company/ASN types, exact ASN/country match, and explicit negative hosting/proxy/Tor/abuse/mobile/satellite/anycast/crawler flags; its VPN flag is tolerated only for this exact VPNGate transport signature. The fixed-line ISP brand list is a positive cross-check, not a standalone proof. Mobile/wireless carriers are not promoted into fixed residential pools.

The XEHN client is a useful implementation reference for a different reason: its `vpngate.go` fetches the same official VPNGate OpenVPN directory and connects those relays through a WARP underlay using Mihomo's native OpenVPN outbound. Its classifier is more permissive than NodeHub's: volunteer relays without a detected hosting signal may be labeled residential, which is not equivalent to verified household broadband. CFNext/cfnew similarly demonstrates a Cloudflare VLESS front chained to VPN Gate OpenVPN nodes. NodeHub borrows the underlay pattern but keeps actual exit-IP, ASN, Layer3 and risk checks; the optional `NODEHUB_CF_FRONT_URI` is a private CI-only probe setting, not a source of residential evidence.

## End-to-end admission remains mandatory

All FreeNodes-compatible source candidates are deduplicated and syntax-checked by the pinned engine, which is configured for a 1,000-node output target. The classification layer then combines that output with up to 310 supplemental VPN Gate/VPNBook candidates under a 1,500-candidate hard ceiling, samples at most 160 across the complete Mihomo-ranked pool, and tests each real exit IP through a strict two-of-three quorum across three independent HTTPS echo services. IPWhois/IPinfo, Layer3 Intel, and O-X-L evidence gates remain unchanged. A node's source label, advertised country, server address, or upstream ping score is never used as proof of exit country, residential status, or low risk.

Source discovery success is not the same as a publishable classified node. If a source yields no compatible nodes or a candidate fails the exit/risk checks, it is recorded as unavailable/rejected and is not inserted into any of the three subscription pools.


## VPNBook official OpenVPN source

The collector reads the official VPNBook OpenVPN page, extracts the current shared credentials and server directory from the page's embedded data, then requests each server's TCP-443 profile from the official `https://www.vpnbook.com/api/openvpn` endpoint using its discovered hostname and IP. If the page's embedded server JSON changes, it extracts the visible official server hostnames and resolves their current public IPv4 addresses through DNS; it does not use stale hard-coded server IPs or legacy ZIP paths. Credentials are held in memory only and are never written to source reports, logs, or diagnostics. If a VPNBook profile passes all classification gates and is published, its required login fields are necessarily included in the public subscription; these are shared credentials already displayed by VPNBook and periodically rotated. Each profile is syntax-checked with the pinned Mihomo binary before it enters the candidate pool. VPNBook contributes up to 10 candidates per run within the 310-node supplemental cap and receives a rotating share of the 160 real-exit probes. Official page: https://www.vpnbook.com/freevpn/openvpn; official configuration API: https://www.vpnbook.com/api/openvpn.
